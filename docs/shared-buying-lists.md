# Shared buying lists and receipt selection

## Workflow
The existing automatic Purchase List and saved whole-box Buying List remain planning tools. The latter's old list is stored locally in the browser. In the saved Buying List, use Share with the buyer, choose a title, active linked employee, due date and instructions, then Save & assign list. This creates an explicit shared snapshot in Snacky OS; it does not erase the local plan or automatically post a purchase. The buyer uses My buying lists / Shared Buying Lists with their own login. A copied page link is private and still requires authorization.

Planned box counts and units/box are fixed for the shared list. The product catalogue's current packaging is rechecked before assignment; unknown/changed packaging is not guessed. Product names, indicative supplier and positive unit-cost estimates are copied from server-side catalogue records, not accepted from client text. Lists can include up to 200 different products. Estimates are not supplier quotations, and missing costs make the total incomplete.

The buyer records Bought, Partly bought or Unavailable per product. Partial/unavailable outcomes require an explanation; actual bought quantities cannot exceed the planned boxes. A list can finish only after every product has a result. Finishing the list is not receiving inventory or approving payment. Continue using the existing purchase, receipt, receiving and payment processes for real transactions. The planner can reassign, cancel with a reason, and reopen a completed list for corrections. Cancellation retains history. Requested quantities cannot be silently changed under a buyer; cancel and issue a new plan if the shopping scope changes.

Plans are visible to the assigned employee, their creator, and authorized purchasing planners. General operator/CRM access to this route does not grant purchase creation, Finance or another buyer's lists. Changes require current active profile and linked team-member permissions, and the database enforces this independently of navigation. Reassignment removes the old buyer's access unless they independently retain creator/planner authorization.

The client stores exact pending command identities before submission. Unconfirmed responses can be retried after reload without creating another list or progression revision. Concurrent stale edits must reload instead of overwriting newer progress. Reload the page to see another device's latest work. This release does not add assignment phone notifications for this new record type, offline synchronization, automatic supplier orders, or automatic conversion into a purchase.

## Print / Save PDF
Open a shared list, select Print / PDF view, then Print / Save PDF. Use the browser's print dialog to choose a printer or Save as PDF. The dedicated A4 view contains the checklist reference/revision, buyer, date, instructions, whole boxes, units, indicative costs, result column and totals. Multi-page tables repeat headings. Printed copies are static: verify the current version before buying. A cancelled list is visibly marked Do not buy. The output is not an invoice, payment proof or stock receipt. No public sharing link is created.

## Mobile receipt input
The manual PurchaseForm and optional receipt-scan form use the same visible native input, with a separately associated label, a large touch target and explicit format/size feedback. No hidden input, asynchronous synthetic click or nested control label is used. Existing receipt_file submission and preview callbacks are retained. Supported formats match the current backend: PNG, JPEG, WebP and PDF, up to 5 MB. Unsupported/oversized input clears the selection with a visible explanation. File selection itself never saves a purchase or starts paid AI extraction.

A physical phone's original failure was not directly observed. Browser acceptance must tap the actual input and receive a filechooser event in Chromium and WebKit; injecting a file alone does not prove chooser activation. Even passing browser tests is not physical iOS/Android Photos/Files/PWA certification. Record any remaining device-specific failure without claiming that a build proves the OS picker works.

## Deployment and verification
Apply only the reviewed CLI-generated 20260920133731_shared_buying_lists.sql after the existing CRM/Company foundation, then deploy the matching application. It creates private checklist metadata and two permission-checked API wrappers; no existing purchases, stock, routes, staff assignments or financial records are seeded or rewritten. The known CRM API allowlist is composed narrowly and refuses an unexpected source anchor. No cron is required. Do not blindly apply unrelated pending migrations.

Before rollout verify backup/rollback procedures, active linked staff access and a real authorized handoff. Keep checklist records and commands on application rollback; do not drop them. The missing-module state reports unavailable rather than pretending the local draft was shared. Existing purchasing remains independent. The concurrent expiry-batch PR must be merged with review of its small overlap in PurchaseForm; this feature does not replace its receipt validation or introduce expiry claims.

The retained workflow runs isolated PostgreSQL access/atomicity/replay/no-money invariants, actual app cross-account browser tests, filechooser taps, PDF content checks, scoped mobile accessibility and the original real integration suites.
