# Company Hub — first release

## Boundaries

The Company area adds reusable instructions and materials to the existing Snacky OS. It does not create a second CRM, task list, payment ledger, inventory system, employee directory or messaging platform. Existing My Work, leads, issues, contacts, locations and obligations remain authoritative. Reading a notice, acknowledging a document and completing work are distinct actions.

This release includes Start Here, How We Work, Documents & Brand, People & Responsibilities, targeted Updates, and owner/admin content management. It has Arabic/English content, role audiences, private drafts, separately published immutable versions, archive/restore, per-version reading and acknowledgement records, private file attachments, approved-for-external-sharing labels, Google Drive/Docs master links, search across titles/descriptions/guide text, 20-row pagination, and a print view. Search does not extract uploaded-file contents.

Seven proposed starter templates cover welcome/first steps, relations responsibilities and first week, visits, customer issues, rent follow-up, operator responsibilities, and approved document/brand use. They are not automatically saved or published. No real salary, private employee record, commercial commitment, logo or approved company presentation is seeded. Review all wording and replace draft descriptions before publication.

## Deployment gate

Default: disabled. `NEXT_PUBLIC_SNACKY_COMPANY_HUB_ENABLED=true` is a build-time application opt-in, not an authorization boundary. Do not enable it for staff before coordinated schema/application rollout and real-role checks. Disabled or unavailable Company materials must not block a route, pickup, stock/cash operation or customer issue.

1. Review and merge the PR only after required checks pass. Maintain a restorable database backup and separate storage-object backup; validate restoration before production rollout.
2. In an isolated/staging environment, verify the five connected-relations migrations `20260915200000` through `20260915200400` are present. The new migration deliberately depends on their auth helpers and CRM storage/API boundaries. It does not install or replace an unrelated PostgREST pre-request hook.
3. Review the pending migration chain before applying `20260916150634_company_hub.sql` through the established migration process. This filename was generated by Supabase CLI 2.117.0 in isolated CI. Do not blindly apply unrelated pending migrations. Nothing in this PR applies SQL to the production project.
4. Deploy the matching application with the feature flag enabled in staging. Verify owner/admin, relations, operator and other staff access, including direct RPC/file requests. Confirm the active profile has its intended linked team member. Investor-only, viewer-only and inactive profiles must not enter Company.
5. Repeat the critical checks below using authorized real sessions before enabling staff use in production. A green build or mocked component check is not live-account end-to-end verification.

For application rollback, disable the flag and redeploy. Keep private versions, receipts and files; do not drop them or weaken storage policies. Preserve compatibility with the connected-relations API guard. The flag does not revoke direct authenticated RPC permissions; database authorization remains enforced independently.

## Initial owner setup

Open Company -> Manage -> a starter template. Review and adapt the Arabic/English wording, purpose/description and approval limits. Set the active content owner and review date. Choose only the roles that should see it. Save creates a private draft; publication is a separate explicit action. Publish only the saved draft you have reviewed.

Prepare the welcome page, the relations role guide, visit procedure, issue procedure and rent procedure first. Add actual current presentation, logos and approved templates under Documents & Brand. Use clear titles such as "Snacky logo - white, transparent" rather than ambiguous final-version filenames. State when each resource should be used, who owns it and whether it is approved to share outside Snacky.

File uploads accept PDF, JPEG, PNG, WebP, SVG, DOCX, PPTX and XLSX up to 4,000,000 bytes. Larger editable masters can use HTTPS links to drive.google.com or docs.google.com. Set sharing permissions at the source: adding a master link does not provision Google Drive access. There is no Drive synchronization, OAuth connection or Drive administration in this release. A live master link is not an immutable historical document. Attach issued proposals, signed agreements, receipts and customer evidence to their original business records. HR documents and salary data do not belong in the general library.

Company files are private and do not get public sharing URLs. "Approved for external sharing" is a management label, not an automatic public-access grant. Staff can download an authorized resource and send it through their normal channel. Browser previews are limited to PDF and raster images; SVG and Office files download as attachments. This is not a malware-scanning service.

Set Notify for meaningful changes. Require acknowledgement only for important role-relevant instructions. Publication targets the selected roles. Existing accounts in those roles, including newly assigned staff, see current outstanding reading. Ordinary staff see the published version, not a later draft. An acknowledgement of version 1 does not acknowledge version 2. Acknowledgement records are retained, including after role changes; the manager report also identifies current role membership. Archiving hides material and alerts from ordinary staff while preserving history.

Give the relations employee actual first leads, current contacts and work assignments through the existing CRM. The onboarding templates are guidance, not an automatically scheduled checklist. Future staff roles must use the existing authorization model; this PR does not grant arbitrary new roles or introduce a custom role editor.

## Safe operating behavior

- Role permissions are enforced in the database and file reads, not only navigation. Raw Company tables in `company_private` have no authenticated direct-table grants. Managers work through checked commands too.
- An open work item's owner, next action and due/review date belong in its native work record. Instructions merely link to those existing screens. Completing a field action does not automatically resolve the customer's issue. Recording rent proof does not create or confirm a financial payment.
- Commands have durable user/item/action/revision identities. Lost responses retain the exact request for retry; successful saves disable the same submission. Changed versions require reloading before another edit. Draft text awaiting confirmation uses session-scoped browser storage. On shared devices, sign out and close the tab before another person uses it.
- Publishing creates a new immutable snapshot. Uploads use immutable object paths and cannot overwrite or delete previously referenced Company objects through normal authenticated access. Keep periodic database and file backups. Administrative orphan cleanup and bulk export tooling are not included.
- Notification counts show outstanding current published materials for the user's roles. Reading a notification never finishes operational work. A failed refresh is explicitly shown as unavailable, not a claim that no updates exist. This feature adds in-app Company notices; it does not send external Company push, email, WhatsApp alerts or scheduled daily digests. Existing route-push behavior stays scoped to its original roles.

## Acceptance and regression checks

Run `node --experimental-strip-types --test scripts/test-company-hub.mjs scripts/test-authz-permissions.mjs scripts/test-connected-relations.mjs`, `npm run typecheck` and `npm run build`. The Company workflow builds with the feature opt-in enabled and runs actual migrations in isolated PostgreSQL 17 using `scripts/test-company-hub-db.sql`. The existing fixture refuses a database name other than `crm_tests`; never run that fixture against production.

Coverage includes private draft/search/attachment access, explicit invalid-version rejection, published/historical content, current and historical audience checks, broad-storage-policy resistance, command replay and stale revisions, read versus acknowledgement, new-version acknowledgement, archive/restore, CRM API boundary preservation, inactive/investor denial and absence of money/task writes. Client tests execute the real editor/action handlers with controlled dependencies for lost responses, double clicks, exact retries and corrupted session data.

Before staff rollout, check real authorized sessions on mobile: create/save/publish a draft; verify draft isolation; upload/preview/download a real harmless file; check Drive access separately; publish a changed version; acknowledge it as the intended employee; verify owner reporting; switch roles and verify restricted direct URLs; ensure a missing Company module does not block native routes, inventory, cash, purchases or issues. Verify task handoffs and rent verification continue to use their existing records.

Remaining later phases: richer per-role onboarding task packages, recurring responsibilities and reminder/escalation automation, daily digests or external delivery, cross-record global search, general employee-private document management, richer Drive integration and custom-role expansion. Add these incrementally against the existing work records, not as parallel systems.
