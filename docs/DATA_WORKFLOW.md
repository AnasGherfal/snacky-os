# Snacky OS Data Workflow

This document defines how development, seed, migration, and production data should move through Snacky OS.

## Data Types

### Temporary local test data

Temporary local test data is anything created by a developer while running Snacky OS locally. Examples include test routes, trial products, one-off inventory movements, fake purchases, temporary machine edits, and UI testing records.

This data is disposable. It may be deleted by `npx supabase db reset`, local database cleanup, or a fresh clone of the project. Do not depend on temporary local data for demos, tests, or shared development unless it has been promoted into `supabase/seed.sql`.

### `supabase/seed.sql`

`supabase/seed.sql` is the repeatable local development baseline. It should contain data that every developer needs after a local reset, such as:

- Local-only development login users.
- A small, useful baseline of machines, products, storage locations, suppliers, team members, and opening inventory.
- Deterministic sample data that is safe to delete and recreate.
- Data converted from approved `docs/current-data` snapshots when the team intentionally wants it in every local environment.

Seed data must be idempotent where possible. It should be safe to rerun during `npx supabase db reset`.

Do not put real production secrets, production user passwords, supplier private terms, or one-off manual testing records in `seed.sql`.

### `docs/current-data`

`docs/current-data` is for current operational snapshots used during the initial migration into Snacky OS. It is a staging area for cleaned source data before it becomes either:

- local development seed data, or
- a controlled one-time migration/import into the real Snacky OS environment.

Use this folder for reviewed CSV snapshots such as starting products, machines, slots, VMS mappings, suppliers, opening stock counts, or initial team lists.

After launch, `docs/current-data` is not the system of record. Snacky OS becomes the system of record.

## Local Reset Warning

Running:

```bash
npx supabase db reset
```

rebuilds the local database from migrations and then reruns `supabase/seed.sql`.

This deletes local manual data that was created through the app or SQL console unless that data is represented in migrations or `seed.sql`.

Use local resets freely during development, but assume every manual local record is temporary.

## Production Rule

Production data must never be reset.

Do not run destructive reset commands against production. Production data includes real products, machines, purchases, routes, team members, inventory movements, cash collections, issues, VMS imports, and audit history.

If production data needs correction, make a controlled application action, an audited admin correction, or a reviewed migration/backfill. Never use local reset habits in production.

## After Launch

After launch, new operational data is added through Snacky OS, not by editing CSV files:

- Products are created and maintained in Snacky OS.
- Machines and locations are created and maintained in Snacky OS.
- Purchases are entered in Snacky OS and create inventory movements.
- Routes are planned and assigned in Snacky OS.
- Team members are managed in Snacky OS.
- Inventory movements are generated by receiving, picking, refilling, returns, waste, and adjustments in Snacky OS.

CSV files can still be used for external imports such as VMS sales or VMS stock reports, but they are inputs to controlled import workflows. They are not the master database.

## Schema Changes

Before launch, migrations may evolve quickly while the MVP is being built.

After launch, every schema change must be made through a Supabase migration. Do not change production schema manually in the dashboard without turning that change into a migration.

Schema migrations should be reviewed, tested locally, and applied in order. Data backfills should be written to be repeatable or clearly one-time, with comments explaining their purpose.
